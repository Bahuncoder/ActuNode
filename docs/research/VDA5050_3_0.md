# VDA 5050 3.0: what changed and what it means for ActuNode

Research note, 10 Oct 2026. Closes PROGRESS issue 9. Decision: [D-15](../DECISIONS.md).

## Sources

- VDA press release, 20 Apr 2026: <https://www.vda.de/en/press/press-releases/2026/260421_PM_VDA_5050_EN>
- Official repository, release `3.0.0` (published 18 Mar 2026, "as released by the VDA on March 19th, 2026"):
  <https://github.com/VDA5050/VDA5050/releases/tag/3.0.0>
- Specification text and JSON schemas compared at tags
  [`2.1.0`](https://github.com/VDA5050/VDA5050/tree/2.1.0) and [`3.0.0`](https://github.com/VDA5050/VDA5050/tree/3.0.0).
- The repository states that where the markdown or schemas differ from the PDF published by the VDA,
  **the PDF is authoritative**. This note is based on the repository; check the PDF before relying on
  a detail.

**Method.** Release notes read in full; the official `state`, `order` and `connection` schemas of
2.1.0 and 3.0.0 flattened to field paths and compared mechanically (added / removed / changed
required flags, types and enums). Spec text checked for topic layout and the new topics.

## Summary

3.0 is a **breaking** release. The topic layout and the message header are unchanged, but many
field names, enums and structures are not. A 2.x fleet manager cannot read a 3.0 robot's state as-is,
and the reverse.

The headline features (zones, path sharing) target **freely navigating robots**; graph-following
robots like ActuNode's simulator are still covered, with renamed fields.

## What did not change

- Topic layout `interfaceName/majorVersion/manufacturer/serialNumber/topic`; for 3.0 the major
  version part is `v3` (e.g. `uagv/v3/ActuNode/robot_01/state`).
- Header fields: `headerId`, `timestamp`, `version`, `manufacturer`, `serialNumber`.
- Order structure: nodes (even sequence ids) and edges (odd), base and horizon via `released`.

## Breaking changes that affect ActuNode

| Area | 2.1 | 3.0 | Where ActuNode uses it |
|---|---|---|---|
| Robot position | `agvPosition` | `mobileRobotPosition` | simulator state, UI map/table, schemas |
| Position trusted | `agvPosition.positionInitialized` | `mobileRobotPosition.localized` | simulator state, schema |
| Battery | `batteryState.batteryCharge` | `powerSupply.stateOfCharge` (+ optional `batteryCurrent`, `range`) | simulator state, UI, schema |
| Emergency stop | `safetyState.eStop`: AUTOACK, MANUAL, REMOTE, NONE | `safetyState.activeEmergencyStop`: MANUAL, REMOTE, NONE | simulator state, schema |
| Operating mode | AUTOMATIC, SEMIAUTOMATIC, MANUAL, SERVICE, TEACHIN | adds STARTUP, INTERVENED; `TEACHIN` → `TEACH_IN` | simulator state, schema |
| Error level | WARNING, FATAL | WARNING, URGENT, CRITICAL, FATAL | simulator errors, schema, UI |
| Action status | WAITING … FINISHED, FAILED | adds PAUSED, RETRIABLE | schema |
| Action states | one `actionStates` array | split into `actionStates`, `instantActionStates` (required), `zoneActionStates` | simulator state, schema |
| Blocking type | NONE, SOFT, HARD | adds SINGLE | order builder, schema |
| Order edges | `startNodeId`, `endNodeId` required | **removed** (edges connect the neighbouring nodes by sequence) | order builder, validator rule `order-sequence` |
| Edge limits | `maxSpeed`, `maxHeight`, `minHeight`, `rotationAllowed` | `maximumSpeed`, `maximumMobileRobotHeight`, `minimumLoadHandlingDeviceHeight`, `reachOrientationBeforeEntering` (inverted meaning) | not used yet |
| Node deviation | `allowedDeviationXY`: number | object (ellipse `a`, `b`, `theta`) | not used yet; schema |
| Connection | ONLINE, OFFLINE, CONNECTIONBROKEN | ONLINE, OFFLINE, HIBERNATING, **CONNECTION_BROKEN** | simulator last will, backend, UI, schema |
| `*Description` fields | e.g. `nodeDescription` | `*Descriptor` (short) vs description (long) | not used |

Behavioural changes worth knowing:

- `startPause`, `stopPause` and `cancelOrder` are **mandatory** for every robot; `cancelOrder` gains an
  optional `orderId`. (ActuNode plans cancelOrder for Week 3 anyway.)
- The first message of a new order always has `orderUpdateId` 0; resending the same `orderUpdateId`
  with different content is an error with a predefined error type.
- Timestamps are specified to 1/1000 s (ActuNode already sends milliseconds).
- New idle definition: empty `nodeStates` and `edgeStates`, all actions FINISHED or FAILED.
- Error types become *extensible enums*: predefined values should be used where they fit.
  ActuNode's own `pathBlocked` / `orderError` must be checked against the predefined list.

## New in 3.0 (not used by ActuNode yet)

- **Zones** (`zoneSet` topic, fleet control → robot, optional): areas with movement rules (restricted,
  one-way, needs authorisation). Robot state reports `zoneSets`, `zoneRequests`.
- **Path sharing**: state may contain `plannedPath` (NURBS trajectory) and `intermediatePath`
  (polyline with ETAs); `edgeRequests` for corridors.
- **`responses` topic** (fleet control → robot, optional): answers to zone/edge requests in the state.
- Translations for error descriptions and hints; hibernation instant actions; `updateCertificate`.

## Problems found in the official material

- **`json_schemas/order.schema` at tag 3.0.0 is not valid JSON**: a trailing comma after the
  `weight` property (line 315). Strict JSON parsers (including Python's) reject the file. Removing that
  one comma makes it parse. Worth reporting upstream (PROGRESS issue 17).
- The release notes say `eStop` was renamed to `activeEmergenceStop`; the schema says
  `activeEmergencyStop`. The schema spelling is used above; confirm against the PDF.

## What this means for ActuNode

1. **Everything ActuNode emits today is 2.x.** A 3.0 fleet manager or robot would not understand it
   (connection enum, position, battery, edges).
2. **The validator would flag every 3.0 message as wrong** (schema, `version-mismatch`) and its
   `order-sequence` rule depends on `startNodeId`/`endNodeId`, which 3.0 removed.
3. The **UI already reads robot data through one set of helpers** (`frontend/src/live.ts`, D-9), so
   reading both versions is a contained change.
4. **Topic configuration already supports `v3`**, but only one major version at a time: the backend
   parses topics for a single configured major version.
5. Who uses 3.0 today is unknown. It is seven months old; installed fleets are likely to be on 2.x for
   a while, but that is an assumption to test in customer discovery, not a fact.

## Status (10 Oct 2026)

Implemented as recommended below (issue 8): validation against the official 3.0.0 schemas on `v3`
topics, 3.0 robots in the robot list and map, orders and replay in each robot's own version and
manufacturer, simulator `--vda-version 3`, end-to-end tests run for both versions in CI. Zones, path
sharing and the `responses` topic remain out of scope.

## Recommendation

Support **2.x and 3.0 side by side**, decided per message by the topic's major version (`v2` / `v3`),
rather than switching. An integration lab is most useful exactly where mixed versions meet. In order:

1. **Week 5 (validation, 6–12 Nov):** validate against the **official** schemas of both versions
   (vendored, with the 3.0 order schema fix noted), selected by topic; version-aware sequence rules
   (`order-sequence` uses sequence ids only for v3). This also resolves PROGRESS issue 7.
2. **Backend and UI:** accept both topic versions; read position/battery/connection through
   version-aware helpers.
3. **Simulator:** a `--vda-version 2|3` option so both can be demonstrated; default stays 2.1.0 until
   discovery says otherwise.
4. **Not now:** zones, path sharing, `responses`. Revisit only if users ask.

Add to the customer discovery questions: *Which VDA 5050 version do your robots and fleet manager
speak today, and when do you expect 3.0?*
