# ActuNode architecture

How the lab is put together, as built. For *why* it is built this way see [DECISIONS.md](DECISIONS.md).
Keep this file in step with the code: when a component, topic or endpoint changes, update it here in the
same commit.

## Overview

```
                        ┌──────────────────────────────────────────────┐
  Browser               │ Backend (FastAPI, Python)                    │
 ┌──────────────┐  HTTP │                                              │
 │ React UI     │──────▶│ missions · failures · sessions · validation  │
 │ map, table,  │       │        │                                     │
 │ stream, ...  │◀──────│ LiveHub ◀── Validator    SessionRecorder     │
 └──────────────┘  WS   │    ▲            ▲              ▲  Replayer   │
                /api/ws │    └──── MqttBridge ───────────┘     │       │
                        └──────────────┬──────────────────────┼───────┘
                                       │ subscribe uagv/#,    │ publish
                                       │ actunode/#           │
                               ┌───────▼──────────────────────▼───┐
                               │ MQTT broker (Mosquitto)          │
                               └───────▲──────────────────────────┘
                                       │ one client per robot
                               ┌───────┴──────────────────────────┐
                               │ Simulator (Python)               │
                               │ Robot state machines, 10 Hz tick │
                               └──────────────────────────────────┘
```

Four processes, each its own Docker Compose service:

| Service | Code | Port | Role |
|---|---|---|---|
| `mosquitto` | [mosquitto/config](../mosquitto/config/mosquitto.conf) | 1883 (MQTT), 9001 (WebSocket), 8883 (MQTT over TLS) | Message broker |
| `simulator` | [simulator/](../simulator) | none | Simulated AMRs speaking VDA 5050 |
| `backend` | [backend/app](../backend/app) | 8000 | REST + WebSocket API, validation, recording, replay |
| `frontend` | [frontend/src](../frontend/src) | 8080 HTTP, 8443 HTTPS (nginx) / 5173 (dev) | Lab UI; nginx proxies `/api` to the backend |

Backend and simulator run as an unprivileged user; Compose runs the backend as the host user so
session files in `./sessions` belong to them (D-12). nginx re-resolves the backend's name per
request, so the backend can be restarted on its own (D-13).

## Security

| Layer | Protection | Decision |
|---|---|---|
| Network | All ports published on 127.0.0.1 unless `ACTUNODE_BIND_ADDRESS` is set | D-18 |
| MQTT | No anonymous clients; per-robot topic permissions (logins `<manufacturer>.<serial>`; ACL generated by `mqtt-init` from `mosquitto/config/acl` plus one block per robot); generated passwords in the `secrets` volume, one read-only subfolder per service | D-23, D-28 |
| Browser | API answers only allowed `Host` names; cross-site WebSockets and state-changing requests refused | D-24 |
| Shared use | Login (API token → HttpOnly session cookie) required; backend refuses to start shared without it | D-25 |
| Encryption | Only HTTPS 8443 and MQTT over TLS 8883 follow the bind address; plain ports always 127.0.0.1; local CA from `cert-init` | D-26 |
| Commands | Orders go only where the request says or to the configured default, never inferred from traffic | D-21 |
| Containers | Backend, simulator and nginx run as non-root users; nginx binds 80/443 via a namespaced sysctl; logs rotate (10 MB × 3) | D-12, D-31 |
| Robot data | Treated as untrusted in the validator and the UI | D-9 |

All parts of issue 12 are done; see README, "Sharing the lab".

## MQTT topics

VDA 5050 layout: `interfaceName/majorVersion/manufacturer/serialNumber/topic`, e.g.
`uagv/v2/ActuNode/<robot>/<topic>`. Both `v2` (2.1.0) and `v3` (3.0.0) are understood (D-15): the
validator picks the official schema set by the topic, and replay restores each robot on its own topic.
Orders go exactly where the mission request says (`manufacturer`, `vda_version`) or to the configured
default (`ActuNode`, `ACTUNODE_VDA_MAJOR_VERSION`); they are **never routed from observed traffic**
(D-21). The live hub tracks one robot per `(major, manufacturer, serial)`, keyed
`v2/ActuNode/robot_01` (D-27, at most 1,000); the identities a serial was seen under are shown in the UI
and produce a `warning` in the mission response when they do not match.

| Topic | Publisher | Subscriber | QoS | Retained | Content |
|---|---|---|---|---|---|
| `uagv/v2/ActuNode/<robot>/order` | backend | that robot | 0 | no | VDA 5050 order |
| `uagv/v2/ActuNode/<robot>/instantActions` | backend | that robot | 0 | no | VDA 5050 instant actions (`cancelOrder`) |
| `uagv/v2/ActuNode/<robot>/state` | robot | backend | 0 | no | VDA 5050 state + `actunode.missionStatus` and `actunode.injectedFailures` (failures currently injected; absent on older robots); every 1 s and on every status change |
| `uagv/v2/ActuNode/<robot>/connection` | robot (and broker, as last will) | backend | 1 | yes | `ONLINE` / `OFFLINE` / `CONNECTIONBROKEN` |
| `uagv/v2/ActuNode/<robot>/factsheet` | robot, on every connect | backend (validated) | 0 | yes | What the simulated robot is and can do (D-34) |
| `actunode/v1/sim/<robot>/inject` | backend | that robot | 1 | no | Failure-injection command `{injectionId, timestamp, robotId, failure, action, params}` (ActuNode, not VDA 5050; failures `BLOCKED_PATH`, `LOW_BATTERY`, `DISCONNECT`, `INVALID_PAYLOAD`, `UNRESPONSIVE`) |

QoS follows VDA 5050 section 6.2: QoS 0 for `order`, `instantActions`, `state`, `factsheet`,
`visualization`; QoS 1 for `connection`. The backend subscribes with QoS 1 (a ceiling, needed to receive
`connection` at QoS 1). The ActuNode inject topic is not VDA 5050 and uses QoS 1 so test commands arrive.

The backend subscribes to `uagv/#` and `actunode/#`, so it also sees its own orders and commands,
which is what puts them in the message stream and in recordings.

## Simulator

| File | Responsibility |
|---|---|
| [robot.py](../simulator/robot.py) | `Robot`: pose, battery, charging, mission status, order acceptance, failure injection, event signature. No I/O. Re-exports the public names of the modules below. |
| [protocol.py](../simulator/protocol.py) | `VersionProfile` per VDA 5050 version (error names, field names, rules that differ), status constants and the state machine summary, limits, payload parsing (D-31 limits) |
| [validation.py](../simulator/validation.py) | Pure order validation: types, id lengths, duplicates, caps (300 nodes/edges/actions) → `Problem` |
| [orders.py](../simulator/orders.py) | New orders, order updates (stitching at the decision point), horizon |
| [instant.py](../simulator/instant.py) | Instant actions: cancelOrder, startPause/stopPause, stateRequest, factsheetRequest, clearInstantActions |
| [messages.py](../simulator/messages.py) | State, connection and factsheet messages per version |
| [publisher.py](../simulator/publisher.py) | `RobotConnection`: one paho MQTT client per robot (own last will); queues incoming orders and instant actions |
| [\_\_main\_\_.py](../simulator/__main__.py) | Main loop (`step`): 10 Hz physics tick; applies queued messages; publishes state every second, on VDA 5050 events and on request; publishes the factsheet on request |
| [topics.py](../simulator/topics.py) | Topic names |

**Mission state machine** (`state.actunode.missionStatus`):

```
IDLE ──order──▶ ACCEPTED ──next tick──▶ MOVING ──last node──▶ COMPLETED ──order──▶ ACCEPTED …
                    │                    │  ▲  │
                    └──BLOCKED_PATH──▶ BLOCKED ─clear─┘
                                         │
                                  battery 0 % ──▶ FAILED ──order (battery > 0)──▶ ACCEPTED …
```

- Orders arriving while ACCEPTED / MOVING / BLOCKED are rejected with an `orderError`.
- Motion: 1 m/s straight lines between nodes; battery −0.2 % per metre; pick/drop actions finish
  instantly on arrival.
- At 0 % battery the robot stops where it ran out and the mission is FAILED (`batteryEmpty`, FATAL);
  orders are rejected until it can drive again (D-17). Robots charge at 1 %/s while they have no active order and stand in the charging zone (D-33); robots in the PARKING zone do not charge (D-37).
- Threading: paho network threads only put messages on a queue; the robot object is touched only by
  the main loop.

## Backend

| File | Responsibility |
|---|---|
| [main.py](../backend/app/main.py) | App, lifespan (start/stop MQTT; close recording; stop replay), health, robots, messages, validation, WebSocket |
| [mqtt.py](../backend/app/mqtt.py), [mqtt_state.py](../backend/app/mqtt_state.py) | `MqttBridge`: one shared paho client, auto-reconnect, subscriptions, message callback |
| [live.py](../backend/app/live.py) | `LiveHub`: latest state per robot, last 500 messages, failure log, validation counters; hands events from the MQTT thread to WebSocket clients on the asyncio loop. The hub stores what a robot last sent as its state even if it fails validation (the inspector shows real traffic), so after an `INVALID_PAYLOAD` `schema` message the robot's position and status may be unknown for about a second |
| [validator.py](../backend/app/validator.py) + [schemas/](../backend/app/schemas) | JSON Schema checks + sequence rules; attaches `issues` to every message |
| [proximity.py](../backend/app/proximity.py) | `ProximityMonitor`: near-collision detection between live robots (`proximity` warning) |
| [vda5050.py](../backend/app/vda5050.py) | Topic names, headers, order building |
| [missions.py](../backend/app/missions.py) | `POST /api/missions` → VDA 5050 order starting at the robot; `cancel` and `extend` (D-35) |
| [sent_orders.py](../backend/app/sent_orders.py) | Memory of the orders ActuNode sent (node contents for order updates), capped, with the lock that serialises missions and extends |
| [failures.py](../backend/app/failures.py) | `POST /api/failures` → inject command; failure log |
| [recorder.py](../backend/app/recorder.py) | `SessionRecorder`: JSONL session files |
| [replay.py](../backend/app/replay.py) | `Replayer`: republishes a session with original timing (asyncio task) |
| [sessions.py](../backend/app/sessions.py) | Recording and replay endpoints; live-robot check before replay |
| [warehouse.py](../backend/app/warehouse.py) | Named locations (metres) |
| [config.py](../backend/app/config.py) | Settings from environment variables |

**Message path:** paho thread → `MqttBridge._on_message` → `LiveHub.handle_mqtt` (under a lock:
validate, store, update robot) → listeners (recorder) → `loop.call_soon_threadsafe` → each
WebSocket client's queue → `send_json`.

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/health` | Version and MQTT connection |
| GET | `/api/session` | Whether login is required and the caller is logged in |
| POST | `/api/login`, `/api/logout` | Exchange the API token for a session cookie / end it (D-25) |
| GET | `/api/locations` | Named warehouse locations |
| GET | `/api/map` | The warehouse map: `size`, `zones` (incl. CHARGING and PARKING), `racks`, `locations` (single source for UI and simulator tests, D-37) |
| POST | `/api/missions` | Send a mission (robot, source, destination, load; optional `manufacturer`, `vda_version`) |
| POST | `/api/missions/{robot}/cancel` | Send a `cancelOrder` instant action (optional `manufacturer`, `vda_version`); 202 with `actionId`, `topic` (D-35) |
| POST | `/api/missions/{robot}/extend` | Order update extending the order the robot reports running (from its own state, if ActuNode sent it) to `to_location` (optional `action`, `manufacturer`, `vda_version`); 409 if unknown, cancelled, foreign or the previous update is unconfirmed (D-35) |
| GET | `/api/robots` | Latest connection + state per robot |
| GET | `/api/proximity` | Pairs of live robots (by key, e.g. `v2/ActuNode/robot_01`) currently closer than `ACTUNODE_PROXIMITY_M` (D-22, D-27) |
| GET | `/api/messages` | Recent MQTT messages with validation issues |
| GET / POST | `/api/failures` | Failure log / inject a failure (`BLOCKED_PATH`, `LOW_BATTERY`, `DISCONNECT`, `INVALID_PAYLOAD`, `UNRESPONSIVE`) with per-failure `params`; clear only `BLOCKED_PATH` and `LOW_BATTERY` (D-42); `UNRESPONSIVE` (`duration_s` 1–300, default 10) keeps the robot connected but silent and deaf to `order` and `instantActions`, ends by itself (D-48) |
| GET | `/api/validation` | Validation counters per rule |
| POST | `/api/validation/reset` | Reset counters |
| GET | `/api/recording` | Current recording |
| POST | `/api/recording/start`, `/api/recording/stop` | Start / stop recording |
| GET | `/api/sessions` | Recorded sessions |
| GET | `/api/sessions/storage` | `{keepDays, maxTotalMb, usedMb, sessions}` (D-41) |
| POST | `/api/sessions/upload?name=` | Upload a session file as the raw body; 413 too large, 422 names the first bad line, 429 an upload is already running, 507 storage full (uploads never delete other sessions) or too little free disk, 408 stalled, 201 returns the session summary (D-41) |
| POST | `/api/sessions/{id}/validate` | Run a saved session through the validator: `{checked, withIssues, byRule, issues (first 100), truncated}`; 409 while recorded, 429 a validation is already running (one at a time, results cached per file state) (D-40) |
| GET | `/api/sessions/{id}/download` | Session file (JSONL) |
| DELETE | `/api/sessions/{id}` | Delete a session (refused while it is recorded or replayed) |
| POST | `/api/sessions/{id}/replay` | Replay a session (`speed`, `include_commands`, `current_time`: each message gets the time it is sent again in `timestamp`, gaps as recorded, non-object payloads unchanged, D-48) |
| GET | `/api/replay` | Replay progress |
| POST | `/api/replay/stop` | Stop replay |
| WS | `/api/ws` | Snapshot, then live events |

Interactive docs: http://localhost:8080/api/docs (served under `/api`, so the UI port reaches them).

### WebSocket events

| `type` | When | Payload |
|---|---|---|
| `snapshot` | On connect | `robots`, `messages`, `failures`, `validation`, `recording`, `replay` |
| `message` | Every MQTT message | `message` (with `issues`), `robot` (updated robot, if any; for a state message whose full payload is in `message`, `robot` omits `state` and carries `stateFromMessage: true`, D-38) |
| `failure` | Failure injected/cleared | `failure` |
| `recording` | Recording started/stopped | `recording` or null |
| `replay` | Replay progress (≈2/s) and end | `replay` |
| `proximity` | Set of near-miss pairs changed (distances refreshed at most once a second, D-38) | `pairs` |
| `validation` | Counters reset | `validation` |
| `sessions` | The session list changed (recording started/stopped, upload, delete, retention) | none: refetch `GET /api/sessions` |

Events are encoded once and the same text is sent to every client. A client that falls behind (its queue
of 1,000 events overflows) is closed with code 1013 and reconnects for a fresh snapshot (D-38); the UI
applies queued events once per animation frame.

### Session file format (v1)

Recording stops by itself at `ACTUNODE_MAX_SESSION_MB` or on a write error, writing an end record with
the reason and telling the UI. Listing sessions reads only each file's first and last line. Replay
streams the file (one pass to count, one to publish), so memory does not grow with session size.


One JSON object per line; see [recorder.py](../backend/app/recorder.py).

```
{"type":"session","formatVersion":1,"sessionId","name","startedAt"}
{"type":"snapshot","robots":[...]}
{"type":"message","t","receivedAt","topic","retained","payload" | "payloadRaw","issues"?}   × N
{"type":"end","endedAt","messageCount","reason"}    reason: stopped | sizeLimit | writeError: …
                                                         (line missing after a crash)
```

## Shutdown

Stopping must never lose data, in whatever order Docker stops the services (on a reboot the broker
can go first).

- **Backend:** the lifespan shutdown stops a running replay, closes an open recording with its `end`
  line, and disconnects from MQTT. WebSocket handlers watch for the close separately, so an idle feed
  cannot block shutdown. uvicorn's `--timeout-graceful-shutdown 5` keeps the whole sequence inside
  Docker's 10 s stop timeout. Covered by `tests/test_shutdown.py` (real uvicorn server).
- **Simulator:** each robot publishes `OFFLINE` if still connected; if the broker is gone it logs and
  carries on. A connection that drops without a goodbye is reported by the broker's last will
  (`CONNECTIONBROKEN`).

## Scenario runner (`cli/`, D-45)

`actunode test` is a separate Python package and a black-box client of the HTTP API (it imports nothing
from the backend). Modules: `scenario.py` (YAML format, strict validation), `client.py` (HTTP, login,
error classification: `StackError` = could not run, `RequestFailed` = the lab refused a step),
`runner.py` (steps in order; `expect`/`never` poll `GET /api/robots` and `GET /api/validation` every 0.25 s;
message conditions read the live feed, `client.Feed`, a WebSocket reader thread (D-46); recording; cleanup), `report.py` (console log, JUnit XML), `cli.py` (arguments, exit codes). Scenario files live in
`scenarios/`.
